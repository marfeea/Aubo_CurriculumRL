# 项目机理知识沉淀

## 执行顺序

1. 完整读取 `.codex/skills/project-engineering-guardrails/SKILL.md`；涉及场景、TCP、IK、Jacobian、接触或控制频率时，同时读取 `.codex/skills/isaaclab-tcp-diffik-debug/SKILL.md`。
2. 运行 `git status --short`，把未提交内容视为用户改动，不覆盖、不回退。
3. 读取 `docs/项目理解.md`、`docs/DifferentialIK课程RL_TCP停靠方案与项目迁移说明.md` 的相关章节，并用 `rg` 定位当前配置、实现、测试和施工记录。
4. 区分四类证据：设计约束、当前代码行为、纯逻辑测试、Isaac 动态实测。没有动态证据时不得声称仿真行为已验证。
5. 先直接回答机理问题，再说明当前项目映射、证据边界和剩余风险。
6. 将可复用且已由仓库证据支持的结论追加或修订到 `docs/项目理解.md`。避免记录一次性日志、未经验证的猜测或重复段落。
7. 文档修改后运行 `git diff --check`，检查目标 diff；代码未改动时不虚报代码测试。

## 回答结构

优先按以下顺序组织：

- 结论：直接说明两种机制是否相同、因果关系是什么。
- 机理：拆分规划/求解层、目标生成层、执行器/物理跟踪层和任务判定层。
- 项目映射：列出当前实际参数、频率、张量或模块位置。
- 证据等级：明确哪些来自代码，哪些来自测试或 Isaac 实测。
- 风险：指出标定、资产、控制频率、饱和、奇异、阈值或评估隔离问题。

## 文档维护规则

- `docs/项目理解.md` 是机理知识的统一入口；迁移说明和施工记录仍分别承担设计事实与验收证据，不复制其全文。
- 每个主题包含“核心结论、机理拆分、当前项目映射、验证状态、风险与后续验证”。
- 新结论与旧结论冲突时，以当前代码和最新动态验证为准，并改写旧段落，不并列保留矛盾说法。
- 数值必须注明单位和作用频率；位置/旋转混合范数不得直接解释为毫米。
- 严格区分 IK 数学求解精度、关节伺服跟踪精度、TCP 标定精度和最终任务成功率。
- 仅在用户要求实现或结论暴露实际缺陷时修改产品代码；普通机理问答只更新理解文档。
